# Release notes for pkpdsim 0.40.0

Two commands, so the analysis of a model runs as one command per part and as a whole: `run_sensitivity` runs the sensitivity analyses a model declares, as `run_credibility` runs its assessment, and `run_pipeline` runs the pipeline of a model, the steps of its analysis one after the other, timed and logged.

## run_sensitivity

The sensitivity analyses of a model were a script of every model package (`python -m <package>.sensitivity.sensitivity_analysis`), with its own options, its own output and no records of its run. The model object declares its runner now, in the field `sensitivities` of the project of sbmlsim, and the command runs it:

```python
MODEL = PKPDModel(
    ...,
    sensitivities={"sensitivity": ".sensitivity.sensitivity_analysis:SENSITIVITY"},
)
```

```bash
run_sensitivity pkdb_models.models.hctz
run_sensitivity pkdb_models.models.hctz sampling --workers 8
run_sensitivity pkdb_models.models.dulaglutide local --subfolders single,multi
run_sensitivity pkdb_models.models.hctz --list
```

It runs the kind `sensitivity` of the run layer into `results/sensitivity`, like the other commands through a staged swap, with the records of the run (`run.json`, `spec.json`, `summary.json`, `progress.jsonl`), `--progress` and `--profile`. The analyses are the names of the analyses of the runner, its default ones without; `--subfolders` selects the simulations of a model whose runners are several (every one by default), `--workers` the processes of the pool. An output written by a sensitivity script before, a folder with the table of the parameters and no records of a run, is replaced like a result of the command.

## run_pipeline

The analysis of a model is a sequence of these commands, and which of them a model runs, in which order and with which options differs between models. A model package declares its pipeline (`pkpdsim.pipeline.Pipeline` of `Step`s, `PIPELINE` in its `pipeline.py`), its model object references it (`pipeline=".pipeline:PIPELINE"`), and `run_pipeline` runs it:

```bash
run_pipeline pkdb_models.models.hctz --list
run_pipeline pkdb_models.models.hctz --cores 12 --skip fit_PK,fit_PD
run_pipeline pkdb_models.models.hctz --from credibility -r /scratch/hctz
```

A step is a command with its arguments after the package; `{cores}` in an argument is the number of processes of a step (`--cores`, the CPUs available by default) and `{results}` the results (`--results-dir`), so a pipeline states where it parallelizes and the machine decides how wide. The steps run one after the other, each in a process of its own: a command parallelizes internally, so every step has the machine to itself, and a step which fails or runs out of memory leaves the results of the steps before it intact; the steps after it are skipped (`--keep-going` runs them). The console shows the steps with their status, time, cores and peak memory and the last line of progress of the running one; a run writes the output of every step, `timings.tsv` (wall time, CPU time of the step and of every process it started, the cores this is on average, the peak memory) and `pipeline.json` (the command lines, the versions and the machine) into `results/pipeline/<time>/`.

The CPU time of a step is the larger of the usage of the processes it waited for and the usage of its process tree sampled from `/proc` every second, since the workers of a pool started by a fork server are not waited for by the step and their CPU time would otherwise be missing.
