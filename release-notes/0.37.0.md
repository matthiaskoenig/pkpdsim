# Release notes for pkpdsim 0.37.0

The libraries of the day: `sbmlsim>=0.39.0`, which carries three changes into a model package. The identifiability analysis of a fit reaches its answer where it used to fail on the last step of a profile, the sensitivity runner of a model gains the polynomial chaos as a fifth analysis, and the factor `integrator` of the credibility verification is a check of its own again instead of a second run of the first method. Nothing of pkpdsim's own code changed since 0.36.0 and no fitted, simulated or generated number of a model moves.

## Dependencies

- **`sbmlsim>=0.39.0`**, which raises the floor of the engine to `sbmlsim-core>=0.25.0` and carries what 0.38.2 and 0.39.0 add.

### A profile which walks into a bound ends there (sbmlsim 0.38.2, sbmlsim-core 0.24.1)

The profile likelihoods of a model fit run through `sbmlsim.fit.identifiability.profile_likelihood`, which walks its points in the engine core where the problem has no gap, and the walk steps in the space the parameter is searched. The way back from that space is not always the number the bound went in as: `10^log10(0.0024)` is `0.0023999999999999994`, one unit in the last place below the bound, which the engine refused as a value outside the bounds of its parameter, so the analysis ended with `the parameter '<id>' is held at <value>, outside its bounds [<lower>, <upper>]` although the walk had asked for the bound itself.

A parameter the data does not determine on one side is what walks into its bound, so the defect met exactly the profiles which say that the data do not determine a parameter, and whether it was reached depended on the bound alone: `0.01` and `10` round trip through `log10` exactly, `0.0024` does not. An analysis whose parameters are all determined was never touched by it, and one which was had no result at all rather than a wrong one. The value a point holds is clamped to the bounds now; a profile which does not reach one is unaffected, bitwise.

### A `ChaosAnalysis` for the sensitivity runner (sbmlsim 0.39.0)

`sbmlsim.sensitivity.pce` had no analysis of the runner to drive it, so the sensitivity runners of pkpdsim could not reach the one method which gives the indices for a few hundred points instead of `n (d + 2)`. `ChaosAnalysis` is the fifth analysis next to `LocalAnalysis`, `SamplingAnalysis`, `FastAnalysis` and `SobolAnalysis`, it reads a Latin hypercube sample into an expansion, writes `S1`, `ST` and, where `second_order` is on, `S2`, and `choose_truncation` picks the basis from the dimension of the model and the number of points instead of raising on the first run. The decomposition which is the cost of the method is taken once per scan now rather than once per candidate degree and observable, measured at 2.9x on the shape of a model of 22 parameters; the expansions are bit identical.

### The factor `integrator` of the verification is a check again (sbmlsim 0.39.0, sbmlsim-core 0.25.0)

This one changes what a credibility report of a model package says. The check reintegrates every adopted fit at the tightened tolerances with the BDF of CVODE capped at a lower order, so a difference which is the choice of the solver and not of the model becomes visible. The engine had no equivalent of `maximum_bdf_order` and dropped the setting, so the second method was the first method: `verification.tsv` gave `integrator` the differences of `tolerances` to the last digit and both were reported as verified, a factor `numerical_solver_error` which no run bounded. It held for every model of the default engine, which is every model package of pkpdsim.

sbmlsim-core 0.25.0 takes the order of the method, the smallest step and the settings of the error test and of the nonlinear solver, so the cap reaches the engine and the two factors are two measurements again. **A verification of a model package made before this release whose `integrator` equals its `tolerances` to the last digit was that defect and is worth running again.** An engine which drops the setting makes the check impossible rather than wrong: COPASI and AMICI take the portable settings alone, the verification names them in `not_applicable`, and `numerical_solver_error` stays `not_assessed`.

## The browser exports

The four committed browser exports of the documentation vendor the runtime of the engine (`engine.wasm`, `compiler.wasm`, `mathlib.wasm`, `sbmlsim-core.js`) and the fingerprints of its files, and their tests compare them with the installed core release, so a move of the core version makes them stale whatever the version is. They are written again with `scripts/cardiovascular_examples.py` and `scripts/lobes_examples.py`.

Nothing of a simulation moves with them. A leaf by leaf comparison of the four datasets against the committed ones shows two differing values per file, `sbmlsim_version` and `sbmlsim_core_version`, and of the twelve `config.json` and `model.json` of the compiled models one each, the core version and the name of the compiler: **every precomputed course and every compiled model description is identical to the last bit**, the compiler of 0.25.0 emitting byte for byte what 0.24.0 emitted. What changed is the runtime itself, which carries the state of the solver in its statistics now.

## Unchanged

- `sbmlutils>=0.17.3`, `pymetadata>=0.9.0`, `pkpdutils>=1.7.1` and `libroadrunner>=2.12.0.dev714` are unchanged, each is still the release pkpdsim was tested against.
