# Release notes for pkpdsim 0.36.1

A patch release hours after 0.36.0, which moves the floors of `sbmlutils` and `sbmlsim` onto the two releases of the day. Nothing of pkpdsim itself changed since 0.36.0 and no number of a model moves, but the floors carry one fix which decides whether a model package can be released at all: the COMBINE archive of a release is written through `sbmlode`, whose printers could not read the wide math of a model, and the releases below are the ones which can.

## Dependencies

- **`sbmlsim>=0.38.1`**, a patch of the simulator which is itself only a refresh of its own floors, `sbmlode>=0.3.3` and `sbmlutils>=0.17.3`, with no behaviour of sbmlsim changed. What reaches pkpdsim through it is the sbmlode fix. `sbmlsim.release.archive.write_archive` writes the ODEs of a model as markdown through `sbmlode.OdeSystem`, and both archive writers of pkpdsim go through it (`pkpdsim.pbpk.archive` and `pkpdsim.perfusion.archive`), so the archive of every release of a model package is written by sbmlode. libsbml reads the flat n-ary sum of a MathML document as a chain of binary nodes, so an assignment rule which sums 1,200 parameters is math 1,200 levels deep, and the printers of sbmlode walked such a chain recursively: the documents of a model with wide math failed with a `RecursionError`, shown as "maximum recursion depth exceeded", so **a model package whose math is that wide could not be released**. The walks carry a stack of their own in sbmlode 0.3.3, a chain of 20,000 terms renders in under a second, and math which nests genuinely deeper than the printers read is refused with an `UnsupportedMathError` which names the depth and the element instead of raising a `RecursionError`. This is a fix in sbmlode which pkpdsim receives through sbmlsim; nothing of pkpdsim's own archive code changed with it.

- **`sbmlutils>=0.17.3`**, the matching refresh of that package. Its `sbmlutils.converters.ode` re-exports sbmlode module for module and therefore carries the same fix, and 0.17.3 moves onto `pymetadata>=0.9.0`, the floor pkpdsim already took in 0.36.0 for the COMBINE archives of the Rust `pymetadata-core`. Nothing of the API which pkpdsim and sbmlsim read changes: the factory, the metadata and the console of the models call what they called before.

## Unchanged

- `pymetadata>=0.9.0`, `pkpdutils>=1.7.1` and `libroadrunner>=2.12.0.dev714` are unchanged, each is still the release pkpdsim was tested against. No behaviour of pkpdsim changes with this release and no fitted, simulated or generated number of a model package moves; the verification of 0.36.0 is reproduced unchanged.
